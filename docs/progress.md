No backend scaffold exists yet, so Postgres provisioning and env setup are deferred until someone starts step 4 (backend from spec).
- Implemented the backend from `api/vibe-check.openapi.yaml` as Vercel serverless functions: `api/vibes.ts` (GET list + POST create), `api/pulse.ts` (GET aggregates), `api/options.ts` (GET static compose choices). `prisma/schema.prisma` adds a single `Vibe` table (Postgres); `lib/pulse.ts` computes team energy/mood/colour board/hype leaders fresh on each `/pulse` read rather than storing a separate aggregate. `lib/constants.ts` mirrors the design's actual `PALETTE`/`EMOJI`/`MOODS` arrays (pulled from `Vibe Check v2.dc.html`) so `/options` matches the UI exactly, including the mood formula (`MOODS[round(avgEnergy) - 1]`, clamped). Per the spec, `colorBoard` omits zero-count colours; `loudestColor` falls back to the first palette entry (count 0) when no vibes exist yet, since the spec marks it required. "Live" vibes are currently just "all rows in the table" — no TTL/expiry — worth revisiting if the wall should only show recent posts. Not yet run/tested: this sandbox has no Node/npm installed, so `npm install` / `prisma generate` / a local request haven't been exercised — next person to touch this should do a real smoke test. Still using polling (`since` param) for live updates, per the spec's existing note. Not yet deployed to Vercel or wired to a real Postgres instance.
